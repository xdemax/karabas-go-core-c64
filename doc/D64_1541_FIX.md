# D64 / 1541: причина `SEARCHING FOR $` и исправление

Дата: 2026-11-09. Основано на разборе `C64_1541_KARABAS_BUNDLE.md` и проверке
реальных исходников `c64_memory.v`, `c64_d64_cache.v`, `c64_machine.v`.

## 1. Причина (подтверждена моделью)

Старый `c64_d64_cache.v` держал `mem_rd` высоким **всё время заполнения
сектора**:

```verilog
else if (ack_d) begin
    cache[fill_i] <= mem_data;
    mem_rd <= 1'b0;
    ...
    mem_rd <= 1'b1;      // последнее присваивание побеждает
end
else begin
    mem_rd <= 1'b1;
end
```

А `c64_memory.v` трактует `d_rd` как **уровень**: пока `d_rd=1`, он каждый
такт запускает новое чтение и держит `d_ack=1`. В результате кэш защёлкивал
один и тот же байт несколько тактов подряд и записывал его в разные индексы:
данные сектора сдвигались/дублировались. 1541 читала мусор, не находила
заголовки GCR, уходила в повторы — C64 висел на `SEARCHING FOR $`.

Проверка на поведенческой модели (D64-порт с level-`d_rd`/`d_ack`):

- старый кэш: **255 из 256 байт неверны** (`cache[0..8] = 3,3,10,17,...`
  вместо `3,10,17,24,...`);
- новый follower: **0 ошибок на 1667 чтениях**.

## 1a. Вторая (главная) причина: полярность IEC

После замены кэша диск всё ещё висел на `SEARCHING FOR $`. Сравнение с
рабочим UnoXT-ядром (`unoxt-c64-core-main/src/c64/c64_zxt.vhd` и
`karabas-go-core-c64-unoxt-test/src/rtl/c64/fpga64_sid_iec.vhd`) показало
разницу:

```vhdl
-- UnoXT: активный высокий (1 = линия прижата)
iec_data_o <= cia2_pao(5);
iec_clk_o  <= cia2_pao(4);
iec_atn_o  <= cia2_pao(3);

-- MiSTer: активный низкий (0 = линия прижата)
iec_data_o <= not cia2_pao(5);
iec_clk_o  <= not cia2_pao(4);
iec_atn_o  <= not cia2_pao(3);
```

`c1541_sd` рассчитан на полярность UnoXT: внутри он делает
`sb_data_in => not iec_data_i` и т.д. В нашем основном ядре стоит
MiSTer-овский `fpga64_sid_iec.vhd`, поэтому **ATN/DATA/CLK приходили на 1541
инвертированными** — привод не видел ATN и вообще не отвечал.

Исправление — инверсия на границе с приводом в `c64_machine.v`:

```verilog
.iec_atn_i(~c64_iec_atn_o),
.iec_data_i(~c64_iec_data_o),
.iec_clk_i(~c64_iec_clk_o),
...
iec_data_d1 <= ~drive_iec_data_o;
iec_clk_d1  <= ~drive_iec_clk_o;
```

Входы MiSTer-ядра (`cia2_pai(7) <= iec_data_i and not cia2_pao(5)`) ждут
активный низкий уровень, поэтому выходы привода тоже инвертируются.

Кэш-баг при этом остаётся реальным (255/256 байт), но одной его правки было
недостаточно: без правильной полярности 1541 не получала ATN.

## 2. Что изменено

### 2.1 `src/rtl/c64_d64_rd.v` (новый, вместо кэша)

Побайтовый follower:

- при изменении `dsk_addr` поднимает `mem_rd` со стабильным `mem_addr`;
- ждёт `mem_ack`, снимает `mem_rd`, выдерживает **≥2 такта** паузы;
- защёлкивает `mem_data` на такт позже `ack` (`CAP_LATE=1`, как старый кэш);
- `invalidate` = `loader_busy`: пока D64-загрузчик пишет образ, захваченный
  байт сбрасывается, после загрузки привод перечитывает уже готовый образ;
- диагностика: `dbg_reads` (число чтений), `dbg_maxlat` (макс. задержка до
  `ack`, должна быть заметно меньше 112 тактов).

`c1541_gcr` меняет `byte_addr` на фронте `bit_clk_en` и использует `ram_do`
только на следующем `bit_clk_en` (≥112 тактов), поэтому асинхронный кэш не
нужен — достаточно, чтобы `dsk_data_in` успевал за `dsk_addr` за десятки
тактов.

### 2.2 `src/rtl/c64_machine.v`

- `c64_d64_cache` заменён на `c64_d64_rd` (`.invalidate(loader_busy)`);
- `.clk32n(1'b0)` — инвертор в клоке убран;
- добавлен импульс `host_loadrom` после `ready` загрузчика: `c1541_sd`
  детектирует смену диска по **спаду** `host_loadrom` (внутри
  `ch_timeout=15000000`, `ch_state` → `wps_n`). Раньше `host_loadrom` был
  жёстко `1'b0`, и привод не видел «вставку диска»;
- инверсия IEC на границе с приводом (MiSTer ↔ UnoXT полярность), см. 1a;
- debug-слова: `3'd1 = dbg_reads`, `3'd2 = dbg_maxlat` (вместо сектора/байта
  кэша).

### 2.3 `src/rtl/iec/c1541_sd.vhd`

Защёлка `ram_do`/`dsk_data_out`/`dsk_wr`/`sd_busy` переведена с `clk32n` на
`clk32` (инверсный клок через LUT — плохая практика; при 112-тактовом окне
дополнительный такт задержки не важен).

### 2.4 `src/karabas_minig.prj`

`rtl/c64_d64_cache.v` → `rtl/c64_d64_rd.v`.

## 3. Ожидаемый результат

История проверки:

- сборка с follower'ом (`c64.kg` md5 `2cfc5347…`) залита, BASIC работает,
  но `LOAD"$",8` на нескольких образах всё ещё висел на
  `SEARCHING FOR $` — это и вывело на полярность IEC (1a);
- сборка с инверсией IEC (`c64.kg` md5 `7ed36549…`, 12:54) **проверена на
  железе**:
  - `LOAD"$",8` → `SEARCHING FOR $`, `LOADING`, `READY.`;
  - `LIST` показывает каталог диска (`... 8 BLOCKS FREE.`);
  - `LOAD"*",8,1` загружает и запускает демо **Coma Light Eleven**
    (Oxyron).
  Скриншоты: `docs/captures/c64_iecpol_list.png`,
  `docs/captures/c64_iecpol_loadstar.png`.

- `LOAD"$",8` показывает каталог (`LIST`);
- `LOAD"*",8,1` загружает первую программу;
- debug `dbg_reads` растёт (~десятки тысяч/с при чтении), `dbg_maxlat`
  заметно меньше 112.

## 4. Если всё ещё не работает

Проверять по порядку:

1. **Данные сектора**: при T18/S0 байты `cache/потока` должны быть
   `12 01 41 00` (первые 4 байта сектора 357). Если нет — смотреть адресацию
   `start_sector_array`/`dsk_addr` и загрузчик.
2. **`dbg_maxlat`**: если близко к 112 — D64-порт не успевает, поднять
   приоритет D64 или уменьшить задержку арбитра.
3. **IEC**: после ATN привод должен тянуть DATA в течение ~1 мс. Проверить
   полярность `c64_iec_*_o` (MiSTer: `iec_*_o <= not cia2_pao(...)`, т.е.
   физический уровень, 0=low) и `not iec_*_i` внутри `c1541_sd`.
4. **ROM 1541**: `sprom_c1541.vhd`, `rom_c1541`; предупреждения XST по
   `c1541_gcr.v` (`gcr_lut`, `gcr_byte_7`).
5. Только после этого — порт MiSTer `c1541_drv`/`c1541_multi`.

## 5. Сборка и проверка

```sh
cd src
make minig FAST=1          # тестовая сборка (~15-20 мин)
# залить src/c64.kg через MSC (см. doc/TOOLS_AND_COMMANDS.md)
```

На плате:

```text
LOAD"$",8          (в BASIC строчными, кавычки — реальные)
LOAD"*",8,1
```

Через serial (если клавиатура недоступна):

```sh
python3 tools/type_slow.py 'load@$@,8' --delay 0.4
```

`@` = PC Shift+2 = C64 `"`.
