# ТЗ: конвертер RGB C64 (VIC-II) → HDMI 720×576@50 для Karabas Mini G

## 0. Задача

Написать синтезируемый модуль на Verilog-2001, который принимает RGB-картинку VIC-II от ядра C64 (UnoXT-ревизия `fpga64_sid_iec`) и выдаёт стандартный цифровой растр **720×576@50** (864×625, 27.027 МГц) для HDMI-передатчика Karabas Mini G (`kg_hdmi_ft`), без использования внешней SRAM.

Модуль должен заменить текущий `c64_video.v`, который сейчас захватывает VIC в полный кадровый буфер во внешней SRAM 504×312 и оттуда выводит картинку. Именно этот тракт даёт баг: машина доходит до BASIC, но в кадре виден только бордюр. Нужен простой и надёжный конвертер по образцу рабочих ядер на этой же плате (Profi и MSX).

Целевая плата: Karabas Mini G, Xilinx Spartan-6 **XC6SLX25-2 FTG256**, ISE 14.7. HDMI: модуль `kg_hdmi_ft`, вход `vga_rgb[23:0]`, `vga_hs`, `vga_vs`, `vga_de`. OSD: `kg_osd_overlay` (рассчитан на текущий тайминг 720×576). Внешняя SRAM под видео **не используется**.

---

## 1. Входные сигналы (от VIC-II)

| Сигнал | Описание |
|---|---|
| `clk_sys` | 31.25 МГц — такт машины, на нём же приходят пиксели VIC |
| `clk_vid` | 27.027 МГц — пиксель HDMI-выхода |
| `reset` | синхронный сброс, активный высокий |
| `vic_r[7:0]`, `vic_g[7:0]`, `vic_b[7:0]` | палитра VIC, 8 бит на канал |
| `vic_hsync` | **`hBlanking`**: высокий во время горизонтального гашения (не путать с обычным sync) |
| `vic_vsync` | **`vBlanking`**: высокий во время вертикального гашения |
| `vic_pixel_ce` | `enablePixel`: **8 импульсов на системный цикл**, т.е. 504 импульса на строку; частота ~7.8125 МГц (при `clk_sys` 31.25 МГц) |

PAL: **504 пикселя на строку, 312 строк, ~50 Гц**. Длительность строки ≈ 64.5 мкс. Во время `hBlanking` VIC выдаёт цвет 0 (чёрный).

Сигналы `vic_hsync`/`vic_vsync` приходят в домене `clk_sys`; их фронты — единственная привязка к кадру. `vic_r/g/b` валидны в момент `vic_pixel_ce`.

---

## 2. Выходные сигналы (точно как у текущего `c64_video.v`)

| Параметр | Значение |
|---|---|
| `H_ACTIVE` | 720 |
| `H_TOTAL` | 864 |
| `V_ACTIVE` | 576 |
| `V_TOTAL` | 625 |
| `rgb[23:0]` | RGB565, развёрнутый в 24 бита: `{r[7:3],3'b000, g[7:2],2'b00, b[7:3],3'b000}` |
| `hs` | активный высокий: `hc >= 720+12 && hc < 720+12+64` |
| `vs` | активный высокий: `vc >= 576+5 && vc < 576+5+5` |
| `de` | активный высокий: `hc < 720 && vc < 576` |

Тайминг **не менять**: под него настроены `kg_hdmi_ft` (`CLKRATE=27027027`, `REF_MHZ=27`) и `kg_osd_overlay` (`H_OFFSET=88`, `V_OFFSET=52`).

Требуемый порт модуля (сохранить совместимость с текущим инстансом в `c64_machine_unoxt.v`):

```verilog
module c64_video (
    input wire clk_sys,
    input wire clk_vid,
    input wire reset,
    input wire [7:0] vic_r,
    input wire [7:0] vic_g,
    input wire [7:0] vic_b,
    input wire vic_hsync,
    input wire vic_vsync,
    input wire vic_pixel_ce,
    input wire pause,
    input wire [1:0] dbg_mode,
    input wire [15:0] dbg_addr,
    input wire dbg_ce,
    input wire dbg_reset,
    input wire dbg_vsync,
    input wire [3:0] dbg_vic,
    output reg        vw_wr,
    output reg [18:0] vw_addr,
    output reg [15:0] vw_data,
    output reg        vr_req,
    output reg [18:0] vr_addr,
    input wire [15:0] vr_data,
    input wire vr_ack,
    output reg [23:0] rgb,
    output reg        hs,
    output reg        vs,
    output reg        de
);
```

Порты `vw_*`/`vr_*` оставить, но **не использовать** (выходы в 0), чтобы не менять инстанс машины. Внешний `c64_memory` можно оставить незадействованным (он будет простаивать).

## 3. Рекомендуемая архитектура (по образцу Profi `hdmi_frame.v`)

Референс: `karabas-go-core-profi-master/src/rtl/hdmi/hdmi_frame.v` — 2-строчный буфер в BRAM, выходные счётчики, сбрасываемые по входному кадру. Для C64 сделать надёжнее: **4 строки** и задержку вывода на **2 строки** относительно входа.

### 3.1. Буфер строк

- 4 строки × 512 пикселей × 16 бит (RGB565) = 32768 бит ≈ 2 RAMB16.
- Реализовать как один массив (`reg [15:0] lbuf [0:2047]`, адрес `{row[1:0], x[8:0]}`) с двумя тактами: запись на `clk_sys`, чтение на `clk_vid`. XST должен вывести true dual-port BRAM (при необходимости `(* ram_style = "block" *)`).

### 3.2. Сторона записи (`clk_sys`)

- `in_line` — счётчик входных строк: сбрасывается по фронту `vic_vsync`, инкрементируется по фронту `vic_hsync` (0..311).
- `wr_x` — счётчик пикселей в строке: сбрасывается по фронту `vic_hsync`, инкрементируется по `vic_pixel_ce` (0..503).
- Пиксель: `pix565 = {vic_r[7:3], vic_g[7:2], vic_b[7:3]}`.
- Запись: по `vic_pixel_ce` в `lbuf[{in_line[1:0], wr_x}]`.
- Никаких пауз/пропусков: 504 пикселя на строку, включая гашение (там VIC сам даёт 0).

### 3.3. Сторона чтения (`clk_vid`)

- Счётчики `hc` (0..863) и `vc` (0..624), так же как сейчас.
- `src_line = (vc >> 1) + 12` — удвоение строк, источник 12..299.
- `src_x = hc * 7 / 10` — аккумулятор (как в текущем `c64_video.v`):
  ```
  acc += 7; if (acc >= 10) { acc -= 10; sx += 1; }
  ```
  так 720 выходных пикселей покрывают 504 входных.
- Адрес чтения: `lbuf[{src_line[1:0], sx[8:0]}]`.
- **Genlock:** сбрасывать `hc`/`vc` не по свободному счётчику, а по входному кадру, но с задержкой: считать фронты `vic_hsync` после `vic_vsync`; когда `in_line == 14`, выдать импульс (через toggle + 2FF в `clk_vid`) и сбросить `hc`/`vc`. Задержка 14 строк = 2 строки «запаса» относительно `src_line=12`: к моменту чтения строки L вход уже записал её 2 строки назад, а строка L+4 ещё не перезаписала её в 4-строчном кольце. Это устраняет гонку чтения/записи.
- Чтобы выходной кадр не «уезжал» из-за разницы частот (вход ~49.7 Гц из-за `clk_sys=31.25` МГц, выход 50.05 Гц), после `vc == V_TOTAL-1 && hc == H_TOTAL-1` **останавливать** счётчики (держать `hc=0`, `vc=V_TOTAL-1`) до следующего кадрового импульса. Тогда кадр удлиняется в вертикальном гашении, без мусорных строк.

### 3.4. Конвейер вывода

BRAM имеет задержку 1 такт. Нужно, чтобы `rgb`, `de`, `hs`, `vs` были выровнены:

```
стадия 0 (комбинационно): addr0 = {src_line[1:0], sx}; de0/hs0/vs0 из hc/vc
стадия 1 (clk_vid): addr1 <= addr0; de1 <= de0; hs1 <= hs0; vs1 <= vs0
стадия 2 (clk_vid): q1 <= lbuf[addr1]
стадия 3 (clk_vid): de <= de1; hs <= hs1; vs <= vs1; rgb <= de1 ? expand(q1) : 0
```

Если по таймингу OSD окажется сдвиг — допускается задержать `hs/vs/de` на столько же тактов, на сколько задержан `rgb` (не более 2–3 тактов `clk_vid`).

## 4. Альтернатива, если 4-строчный буфер не заведётся

MSX-подход (`karabas-go-core-msx-master/src/rtl/msx_video.v`): полный кадр **активной области** в BRAM.

- Хранить только 320×200 пикселей (видимое окно VIC) × 4 бита = 250 Кбит (~14 RAMB16).
- Писать по `vic_pixel_ce` в моменты, когда VIC показывает активную область (или просто по координатам `x=0..319, y=0..199`, отсчитывая от `vsync/hsync` с известными задержками).
- Выводить 720×576: картинку 640×400 (или 320×200 с 2×) в центре, вокруг — текущий цвет бордюра VIC (запоминать `$D020`/цвет бордюра по первому пикселю строки).
- Плюс: не нужно ловить фазу строк; минус: теряются эффекты в бордюре (спрайты/FLD/открытый бордюр).

Этот вариант допустим как fallback, но основной — 4-строчный Profi-подобный.

## 5. Ограничения и требования

- Verilog-2001, синтез ISE 14.7, без сторонних IP и без деления на переменную.
- Никаких защёлок, все регистры с синхронным сбросом.
- Внешняя SRAM не используется; `vw_*`/`vr_*` = 0.
- Уложиться в ~2–4 RAMB16.
- Не менять тайминг 720×576/864×625 и полярность `hs/vs/de`.
- Корректно переживать отсутствие/дребезг `vic_vsync`: до первого кадра выход чёрный, счётчики не уходят в X.
- PAL обязателен; NTSC (262 строки) — по возможности, но не приоритет.

## 6. Что предоставить

1. Готовый `c64_video.v` с указанным портом.
2. Краткое описание, как выровнены конвейеры и почему нет гонки записи/чтения.
3. Оценку ресурсов (RAMB16/LUT) и тайминга.
4. Тестовый план:
   - blink-тест: писать в буфер красный/зелёный каждые ~0.5 с — картинка должна мигать;
   - raster-тест: `LDA $D012; AND #$0F; STA $D020` — должны быть горизонтальные полосы;
   - обычный KERNAL — экран BASIC;
   - OSD (`Menu+Esc`) — не должен съехать.

## 8. Контекст отладки (что уже проверено)

- C64-машина стартует до BASIC: вехи M1 (очистка экрана), M2 (BASIC скопировал CHRGET), M3 (баннер) = 111.
- VIC-тайминг правильный: 504 `pixel_ce` на строку, ~311 hsync на кадр, `rasterY` меняется раз в строку.
- Захват в SRAM и вывод живые: тест мигания красный/зелёный проходит.
- VIC-состояние: `DEN=1`, `rasterEnable=1`, фон 6, бордюр 14; но `LRBorder=1` по всей строке — окно экрана не открывается в текущем тракте.
- Причина, скорее всего, в геометрии/синхронизации SRAM-тракта, а не в VIC. Поэтому нужен простой BRAM-конвертер.

## 9. Итог реализации (2026-11-09)

Реализовано в `karabas-go-core-c64/src/rtl/c64video.v` (обёртка —
`src/rtl/c64_video.v`):

- 4 строки × 512 × 16 бит в BRAM (2 RAMB16), запись на `clk_sys`, чтение на `clk_vid`;
- `sel_line = min(номинальная_строка, последняя_записанная)` — компенсирует
  разницу длительности входной/выходной строки;
- genlock по кадру VIC, `src_x = hc*7/10`, удвоение строк;
- параметры по умолчанию: `SRC_LINE0=12`, `LAG=2`, `X_LOAD=0`,
  `MASK_BLANK=1`, `STALL_MAX=40`.

Проверено на Karabas Mini G:

- `c64` (MiSTer-машина) — BASIC V2, OSD, стабильная картинка;
- `c64u` (UnoXT-машина) — то же.

Тестовая ветка `c64u2` после проверки удалена; `c64u` оставлен как запасной.
